SH-04

Library Search & Relevance

Visrez platform · Rails

What is actually there

Every property of a library object — the ones a librarian typed and the ones the database derives — is flattened by triggers into a single FULLTEXT-indexed string per object, in library_object_properties_concatenated.values. Search runs MATCH(…) AGAINST(? IN BOOLEAN MODE) against that column.

The interesting part is that the same SQL fragment is reused three times: as the WHERE predicate, as a selected column (which is where the match score comes from), and as the first ORDER BY term. Scores are then normalised to 0–1 against the maximum for that query — and because MAX() is an aggregate that would collapse the result set, the maximum is pulled from a re-selected copy of the same relation used as a scalar subquery. Selecting a computed column alongside the entity needs objects_query.arel.projections, because Rails' own #select loses the entity columns once a MATCH expression is in play.

Query text gets massaged before it ever reaches MySQL: bare numbers are wrapped in quotes so 8 stops matching 81, and a trailing seats / pax / size is folded into the same quoted phrase. Getting one- and two-character terms to index at all needed innodb_ft_min_token_size = 1 on the server, which is documented in the repo's README.

The front end searches on every keystroke without hammering the server: in-flight requests are held in a map keyed by the serialised form, an identical query is dropped outright, a superseded one is abort()ed, and the survivor goes out behind a 50 ms leading-edge throttle.

Why it earns a sheet

It is the one piece of backend work on the CV that has an obvious picture: type, and watch relevance bars sort themselves. The demo can show the SQL alongside the result, which is the part a reader cannot otherwise see.

The Generated SQL layer prints the real query template with the live query interpolated and highlights the three places the match fragment is reused as the user types — that reuse is the point of the sheet.

SH-05

Synthetic Properties

Visrez platform · Arel

What is actually there

A library object stores its size as one string: 160x80x74. Nobody searches for that. People search for 5ft3in, or 1.6m, or 63". So the schema grows a table of synthetic properties — rows the database derives and maintains itself — and those rows feed the same FULLTEXT column SH-04 searches.

LibraryObject.size_synthetic_property_select_sql builds it with a recursive CTE named split_sizes: SUBSTRING_INDEX takes the head, a CASE expression keeps the remainder, and the CTE recurses until nothing is left, producing one row per dimension. Six projections then render that set six ways — Size (centimeters), Size (meters), Size (in"), Size (inches), Size (ft'in"), Size (feet-inches) — each GROUP_CONCATed back together with SEPARATOR ' by ', and union-alled. Seat counts get the same treatment with two aliases, Pax and Seats, so either word finds them.

The part worth putting on a sheet: those same Arel builders are also the body of the after_insert / after_update / after_delete triggers. One Ruby definition produces both the backfill query and the trigger SQL, so the two cannot drift. A second trigger layer, on the synthetic table itself, re-concatenates every property of the touched object into the searchable string with an ON DUPLICATE KEY UPDATE upsert. Writes stay ordinary Rails writes; the search index maintains itself.

Why it earns a sheet

It is a data-flow story, and data flow draws well. It also pairs with SH-04: this sheet explains where the searchable text comes from, that one explains what happens to it.

SH-06

Library Tagging Tool

Visrez platform · progressive HTML

What is actually there

A screen for putting values on hundreds of library objects quickly. Objects are grouped by subcategory and by style clique. A property schema can be marked shared in group, which means every object in the clique takes one value — so the tool gives the group a single input, and mirrors what you type into each member's own field as you type it.

The mirrored fields are real inputs, but they are not focused, so they get no caret. The tool draws one: each form carries a --caret custom property set from the shared input's selectionStart, and CSS positions a blinking pseudo-element from it. The index is clamped to lastIndexOf(' ', selectionStart), because the advance metric counts spaces twice and the fake caret would otherwise drift right of the real one.

Around that: in-place editing everywhere (label, pencil, input, tick, undo — .with-in-place-edit / .in-place-edit-always), <datalist> autocomplete built from values already used for that schema, a tab order that walks the grid, a toggle that shows only the objects still missing the property, and a hard 250-object page cap with an explicit "results hidden" warning rather than a silent truncation. Saving is one find_or_create_by, and clearing the field deletes the row instead of storing an empty string.

Why it earns a sheet

Of the five, this is the one that is already a picture, needs no backend at all, and shows interaction-design judgement rather than SQL. Build it first. The simulated caret is the kind of detail that reads as care.

SH-07

Event Dispatch & Module Discovery

GNU social v3 · Symfony

What is actually there

GNU social v3 is built out of 19 components and 34 plugins that never call each other. They talk through events. App\Core\Event is a thin wrapper over Symfony's dispatcher that keeps the older, terser GNU social API — Event::handle('Name', [&$arg]) — while the dispatcher underneath does the priority ordering.

A module never registers a listener by hand. Any class in components/*/ or plugins/*/ is a module, and every public method on it named on<EventName> becomes a listener for that event. That discovery happens in a compiler pass, at container build time, by reflection — so the wiring costs nothing at request time and appears in the compiled container.

The same pass is where the safety net sits. It reads each handler's declared return type and throws BugFoundException if it is not EventResult, so a plugin with the wrong signature fails the build rather than a request. EventResult is a three-case enum: next keeps the chain going, stop halts propagation and tells the emitter someone claimed the job, unhandled says so explicitly. That third value is what lets emitters write a default branch: if (Event::handle('X', $args) !== Event::stop) { … }. A runtime check catches handlers that return nothing at all and names the offending file.

Twig gets the same mechanism through a handle_event() function, so a core template can accumulate blocks contributed by plugins — that is how attachment rendering is extended without core knowing which encoders exist.

Why it earns a sheet

GNU social is the largest thing on the CV and has nothing visual on the page. Dispatch is genuinely animatable, and toggling plugins on and off shows why the architecture was chosen far faster than the paragraph above does.

SH-08

schemaDef → Doctrine Metadata

GNU social v3 · Doctrine

What is actually there

Doctrine wants schemas as attributes, XML or YAML. GNU social v2 described tables as plain PHP arrays, and that format is better to read and to diff, so v3 kept it: every entity implements abstract public static function schemaDef(): array, returning table name, description, fields, primary key, indexes, unique keys and fulltext indexes.

SchemaDefDriver makes Doctrine accept it. It extends StaticPHPDriver, is attached to doctrine.orm.default_metadata_driver by a compiler pass, and redefines isTransient() to mean "has no schemaDef method" — so being an entity is a property of the class, not of a registration list. loadMetadataForClass then translates the v2 vocabulary into Doctrine's: varchar→string, serial→integer with an auto generator, tinyint→smallint, numeric→decimal; size is folded into the type name, not null is inverted into nullable, char becomes a fixed-width string, per-field description is hoisted into the column comment so the documentation lands in the database itself, and ['idx_name' => [cols]] maps are reshaped into the [['name' => …, 'columns' => …]] form Doctrine expects.

Because plugins are discovered by the same compiler pass, a plugin that ships an Entity/ directory gets its own tables registered against the same driver — a plugin extends the schema by existing. And a PHPStan extension closes the loop on the query side: DB::find('actor', …) takes a table name as a string, and the extension boots the real kernel during analysis so static analysis still types that call as Actor|null.

Why it earns a sheet

It is a transform, and transforms are the easiest thing to show honestly: input on the left, output on the right, one rule at a time. It also pairs with SH-07 — same compiler pass, same "modules extend the core by existing" idea, seen from the data side.

SH-09

Fediverse Playground

Own tool · Bun + TypeScript · GPL-3.0

What is actually there

A CLI that turns one YAML file into a working fediverse on a laptop: several GNU social nodes (v3 and v2), each on its own hostname and TLS certificate, all federating with each other through one nginx. It exists because testing federation needs at least two servers that believe they are different sites, and the Python/whiptail tool it replaced could not do that. 51 commits, all yours, on a public repository.

Three mechanisms do the work. Worktrees: one bare mirror per software under mirrors/, one git worktree per instance, so Alice can run branch v3 while Bob runs main of the same repo; if a branch is already checked out by another instance the manager creates <branch>-<instance> instead, falling through local branch, remote-tracking branch, new branch. Recipes: each software declares its dependencies (web, db, redis, mariadb) with a shared flag and a buildContribution() that returns services; the builder emits shared services once, deep-merges contributions with array concatenation, collects the web volumes and web depends_on, and refuses to write a compose file whose depends_on names a service that does not exist. Hostnames: every *.localhost name gains a *.fediverse alias, and the resolved list is written both as an /etc/hosts snippet and as files/hosts.nix, which the flake exports as a NixOS module setting networking.hosts.

Each instance is two containers: a one-shot <id>-install that waits for Postgres to be healthy, runs composer, creates the schema, and seeds an admin by booting the real Symfony kernel and calling DB::persistWithSameId; and the app container, which depends_on the installer with service_completed_successfully. The nginx server block is not hand-written: the recipe rewrites the repository's own docker/nginx/nginx.conf with a handful of regexes, and the certificate is minted with openssl -addext subjectAltName over every hostname the instance answers to.

Why it earns a sheet

It is the infrastructure behind the GNU social work, it is public, and it is a graph problem that draws itself: config on the left, the generated service graph on the right, shared services appearing exactly once no matter how many instances you add. Systems breadth in one picture — git plumbing, Compose, nginx, OpenSSL, Nix — without a single screenshot of a web page.

Proposed implementation

} as const;

The live layer is three toggles — Alice (v3), Bob (v3), a v2 node — and the generated graph beside them. The compose builder is pure TypeScript once the filesystem calls are stubbed, so port the merge logic rather than faking it: shared services dedupe, install → app gating, web depending on every app. Show the YAML that would be written in a collapsible pane. The Worktrees layer draws the branch-collision rename; the Installers layer is a short sequence diagram (db healthy → installer completes → app starts); the Hostnames layer fans one name out to the snippet, the hosts.nix attribute set, and the module.

The archived Visrez deployment tool (see bench) is the same idea, earlier and private — mention the lineage in the subtitle, do not show it.

SH-10

Offline-first Votes: patched player → D1

Own tool · Kotlin + Java + Astro/Workers

What is actually there

A full pipeline from a modified Android video player to a Cloudflare D1 database, built so a personal video library could be rated and its watch time measured with no server assumed to be reachable. Two repositories: fourteen bytecode patches for MX Player 3.1.1 (public, GPL-3), and a small Astro + Workers API with a D1 schema.

Patching. The patches run on Morphe, a ReVanced-lineage patcher. Fingerprints are anchored on string constants unique to the method ("#EXTMXOPT:autogen=true,…") rather than on obfuscated names like E6, which do not survive a build. Options such as the server URL are baked in at patch time by rewriting a method body to const-string v0 / return-object v0; icon ids are read at runtime with sget from the app's own generated resource class. One commit message records the trap worth a diagram: the click dispatcher declares 21 locals, so p0/p1 are out of range for iget-object and invoke-static; naming them directly gets the instruction silently dropped and a VerifyError at runtime, so they are copied down with the /from16 forms first.

Client. A Java extension keeps a SQLite queue. Vote rows are inserted held: one revocable vote per watch session, invisible to the sync worker until playback moves on, released on next start if the process dies. Each row carries a client-generated UUID. A sync pass posts a batch, and only rows the server confirms are deleted. Watch time is sampled every two seconds by a lifecycle-bound timer, reading position and duration reflectively off the obfuscated player; if the members cannot be resolved the feature switches itself off. Segments are recorded as ordered [start, end] pairs with overlaps preserved.

Server. /api/sync takes up to 500 events, processes each independently, and is idempotent on the UUID primary key of vote_events and watch_events. Identity is resolved down a ladder: file_hash (SHA-1 of the first 2 MB plus last 256 KB, the same scheme the local catalogue used to match 1101 renamed files back to their originals), then source_url with the query string stripped, then name plus duration within ±2 s, then name alone. watch_segments are deliberately not merged on write — a section watched three times reads as three — because coverage can be collapsed later and repetition cannot be recovered. The same repository also holds the diagnosis of why the player could not open a playlist file at all: ffmpeg's HLS demuxer claims any file starting #EXTM3U and plays the entries as segments of one stream, which explains the dead seek bar, the wrong title and next-track walking the folder in one stroke.

Why it earns a sheet

Nothing else in the directory spans reverse engineering, Dalvik bytecode, an offline-first client, and a serverless backend with a real idempotency story. The demo is a state machine, and state machines animate well: vote, go offline, watch the queue grow, come back, replay the batch, and the counts do not move.

SH-11

web-ts-mode

Own tool · Emacs Lisp · tree-sitter

What is actually there

One Emacs major mode for every nested web language you actually edit: HTML, JS, TS, JSX, TSX, CSS, SCSS, XML, SVG, Astro and Vue. About 3,700 lines of Lisp across the core and seven host files, 50 ERT tests plus a perf suite, a Nix flake, and a bin/web-ts CLI with grammars, doctor, test, compile and bench. 47 commits, all yours, public.

The interesting part is how the nesting is done. Each host uses native treesit-range-rules with :local t, so every embedded region gets its own parser instance. For Astro, a whole html_interpolation minus its braces (:offset '(1 . -1)) is handed to the TSX parser as one program, so an object literal followed by JSX parses correctly instead of splitting at the first tag; interpolations nested inside another are excluded by a parent-until check, and lang="scss" on a style tag selects the SCSS grammar rather than CSS. Comment syntax follows treesit-language-at — markup, C-like, or block — through comment-setup-function on Emacs 31 with a post-command fallback.

Selectors are painted by depth: a recursive walker over combinator chains and the arguments of :not() / :has() assigns each leaf a nesting level, and a face is generated per level by moving the hue from a base toward an end hue with clamped lightness, cached per depth. a > b > c deepens left to right; comma branches share a depth. Eglot is the default client with whole-file servers only; a missing grammar degrades the buffer rather than killing it; M-x web-ts-doctor reports Emacs version, grammars found, and language servers on PATH.

Why it earns a sheet

Syntax highlighting is already a picture, and the multi-parser story is invisible everywhere except in a diagram. It also says something the other sheets do not: you build your own tools when the existing one (web-mode, 2014-era regex fontification) is not good enough, and you finish them — tests, doctor, bench, packaging.

SH-12

:global() with a leading combinator

Astro compiler-rs · Rust · fork branch

What is actually there

A fix to Astro's Rust compiler for scoped styles. With CSS-modules mode off, lightningcss parses :global() as an opaque CustomFunction with a token list, and the scoper silently ignored it whenever the argument started with a combinator — so .a :global(> .b) scoped .b as if it were local. The change adds a visitor that re-reads the argument text out of the source, splits off a leading combinator, parses the rest into a real Selector, normalises it to PseudoClass::Global recursively, and hoists the combinator out before scoping runs. 640 lines in css_scoping.rs, a changeset, and two new test files. A sibling commit fixing JSX inside object literals (#58) is already on upstream main; this one is still on your fork.

Why it earns a sheet

It is the only Rust in the directory, and the CV is built on Astro. A selector going in and the scoped selector coming out is a two-line demo that anyone who has written a scoped style understands instantly. Verdict is maybe only because it may sit better as an inline example inside the contributions section than as a full sheet.

Proposed implementation

// src/components/GlobalScopingDemo/Demo.astro

House rules for whoever builds these

Every existing demo has the same shape, and these should too. Copy src/components/SpaceBuilderDemo/Demo.astro as the reference rather than inventing a structure.

  • One directory per demo under src/components/, with Demo.astro at its root and a layers/ subdirectory of one .astro file per layer.
  • Demo.astro declares a layers map (as const), passes it to TechnicalDrawingStack along with subtitle, scale, size, date and tech, and fills the layers and aside slots with a function keyed by layer id.
  • The first layer is the live one and takes name: null; supporting layers take pageStyle: 'blueprint'.
  • Each layer gets a PostIt in the aside slot saying what to do with it, in the second person, one or two lines. The sheet's fold picks up the note's colour automatically, so the colour is a real choice.
  • tech names come from src/server/tech-icons.ts. All of rails, ruby, mysql, php, symfony, css3 and javascript already exist — no new icons needed for any of these five.
  • Anything heavy mounts through bootWhenVisible from src/client/bootWhenVisible.ts: after DOMContentLoaded, on an idle callback, when the island scrolls into view. SH-06 and SH-08 should need no island at all.
  • Autoplay yields to the visitor on hover or focus, and everything animated respects prefers-reduced-motion.
  • Colours come from the tokens in src/scss/_colors.scss — --ink, --line-strong, --surface-sunken, --blueprint — never literals, because every theme has to keep working.
  • Register the demo by importing it in src/pages/index.astro inside #demos, and tick the matching line in TODO.md.

Source repositories are local: ~/projects/visrez/platform/repository (branch hs-1946-arel for all three Visrez sheets) and ~/projects/gnu-social. Neither is public in the state these sheets describe, so demos must be rebuilt from mock data, not lifted.

For review

Eight demos is a lot of page. Should SH-04 and SH-05 be one sheet?

They are two halves of one pipeline — SH-05 makes the text, SH-04 searches it — and merging them would give one six-layer stack instead of two four-layer ones. Splitting keeps each stack short; merging tells a better story.

Do the two GNU social sheets sit in Demos, or somewhere new?

They are diagrams about architecture, not interactive products, and the existing three demos are all products. A separate section, or an architecture-flavoured sheet style, might frame them better than dropping them in the same run.

How much Visrez internal detail is publishable?

The sheets as drawn name table and column names and show query shapes. Nothing proprietary about the object library itself is exposed, and thumbnails would be placeholders — but that is a call to make before building, not after.

Build order?

Suggested: SH-06 first (no backend, immediately visual, proves the tagging story), then SH-08 (mostly static, cheap), then SH-04 and SH-05 together, then SH-07 — the animated bus is the most design work of the five.

Is SH-10 something you want on the CV at all?

The patch repository is public under your handle and the engineering is the strongest full-stack story in the directory, but the library it serves is personal. The sheet is drawn so that nothing from the library appears, and the source is described only as "a personal video library". Approve, approve with a different framing, or drop it.

Which of the upstream patches were actually submitted?

The git patch is on your fork; libinput, Hyprland, t3code and claude-auto-retry exist only on local branches; the compiler-rs JSX fix is on upstream main and the :global fix is not. "Contributed", "proposed" and "carried locally" are different sentences in the contributions section.

Do the tooling sheets form a second run?

SH-09, SH-10, SH-11 and SH-12 are tools you built for yourself or fixes to tools you use; SH-01 to SH-06 are products. Twelve demos in one run is a lot of page. A second run titled along the lines of "Tooling" would let the two GNU social architecture sheets (Q2) sit with them.
